# Contributing to nfsetable

Thanks for helping! This guide covers the setup, the conventions and how to send changes. To see
how the pieces fit together, also read [AGENTS.md](AGENTS.md) (a short map of the code and its
rules).

**Issues and pull requests in Portuguese are welcome**, and so are English ones.

## Privacy first

NFS-e invoices carry names, CNPJ/CPF numbers (Brazilian company and personal tax IDs), addresses,
bank details and amounts. So:

- **Never** attach real invoices, names, CNPJ/CPF numbers, values or personal paths (such as a
  folder with your name or your synced drive) to issues, tests, fixtures, examples or pull
  requests. Not even a redacted PDF: PDFs can keep hidden text and metadata.
- Use synthetic data: "EMPRESA EXEMPLO LTDA", CNPJ 00.000.000/0001-91, "Cidade Exemplo - UF" and
  made-up amounts.
- The test PDFs in `crates/core/tests/fixtures/` are **synthetic**, generated by code
  (`crates/core/examples/gen_fixtures.rs`).
- To report a layout the app does not read, describe it (use the "Nota não lida" issue template)
  or reproduce its positions in a synthetic PDF. If you paste a profile you saved in the app,
  check it first: its fingerprint or anchor texts may contain a CNPJ or a name.

## Setup

Prerequisites are in the README, under [Building from source](README.md#building-from-source).
Then:

```sh
bash scripts/fetch-pdfium.sh    # or scripts/fetch-pdfium.ps1 in PowerShell
cd app && npm install
```

PDFium goes to `vendor/pdfium/<platform>/` (ignored by git). The Rust tests and the desktop app
need it; the UI in the browser does not.

Everyday commands:

| To | Run |
|---|---|
| Test the engine and the backend | `cargo test --workspace` |
| Format and lint | `cargo fmt --all` and `cargo clippy --workspace --all-targets -- -D warnings` |
| Run the UI in the browser, with sample data | `npm run dev` (in `app/`) |
| Type-check the UI | `npm run check` (in `app/`) |
| Run the desktop app in development | `npm run tauri dev` (in `app/`) |
| Read a folder from the terminal | `cargo run -p nfsetable-core --example extract -- <folder>` |
| Regenerate the fixtures | `cargo run -p nfsetable-core --example gen_fixtures` |

### Trying the real app without touching your data

Development builds use the same data folder as the installed app. When you run the desktop app to
try something, set `NFSETABLE_DATA_DIR` to a throwaway folder and, on Windows, also set
`WEBVIEW2_USER_DATA_FOLDER`, so the WebView storage is isolated too. Automated end-to-end runs
must always do this, and must never clear storage or move the real data folder around.

## Checks before a pull request

CI runs these on Ubuntu and Windows. Run them locally first:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cd app
npm run check
npm run build
```

## Conventions

- **Language:** everything in the repository is in English (code, comments, file names,
  identifiers, JSON keys, docs), except what the user reads: UI text, user-facing error messages
  and warnings, the sources and notes in `crates/core/tax/br.json`, and `README.pt-BR.md`, all in
  Brazilian Portuguese. Tax terms with no real translation keep their names (`danfse`, `das`,
  `fator_r`, `pro_labore`, `rbt12`).
- **Money** is always integer cents in the contract (`i64` in Rust); never floats. The tax engine
  computes with `rust_decimal` in reais and rounds to the cent, half away from zero, at each step.
- **Coordinates** are PDF points with the origin at the top-left corner of the page as it is
  displayed (rotation already applied). Only the rectangle of a region rule is relative (0 to 1).
- **Extraction is positional:** a rule finds a label and reads the value below it or to its
  right, or reads a region. Never parse values with regular expressions over the text flow.
- **The contract** between engine, backend and UI is `crates/core/src/model.rs`, mirrored in
  `app/src/lib/types.ts`. If you change one, change the other in the same PR (the
  `json_shape_matches_the_frontend_types` test helps catch drift).
- **The browser mock** (`app/src/lib/mock.ts` and `app/src/lib/mock-tax.ts`) lets the UI run
  without Tauri, and `mock-tax.ts` mirrors the tax engine. Change it together with the engine.
- **PDFium is not thread-safe:** code that uses `Engine::pdfium()` directly must hold
  `Engine::lock()`.
- **Everything local:** no network calls, telemetry or resources loaded from a CDN.

## Adding a built-in profile

Profiles describe how to find each field in a known layout.

1. Create the JSON in `crates/core/profiles/` (use `danfse-national.json` as a model):
   - `id`, `name` (shown in the UI, in Portuguese) and `builtin: true`;
   - `fingerprint`: text snippets that identify the layout. All of them must appear in the
     document (compared without accents, case or spaces);
   - optionally `namePatterns` (file name patterns with `*` and `?`), `docType` (e.g. `"NFS-e"`)
     and `kind` (`"revenue"` or `"expense"`);
   - `fields`: rules per field id (`net_value`, required; `service_value`; `competence`), tried in
     order. An `anchor` rule finds a label by regex (over the normalized text: lowercase, no
     accents, with `\s*` between words) and reads the value `below` it (same column) or to its
     `right` (same line), up to `maxDistance` points. `excludeSuffix` rejects label occurrences
     followed by a given text, such as "Valor Líquido da NFS-e + IBS/CBS".
2. Register the file in `BUILTIN_PROFILE_SOURCES` (`crates/core/src/profile.rs`) and update the
   unit tests there that check the built-in list.
3. Reproduce the layout in `gen_fixtures.rs` with made-up data, regenerate the fixtures and write
   a test in `crates/core/tests/extraction.rs`.

A profile saved by the app (Perfis menu) already has this format and is a good starting point.

## Synthetic fixtures

- Every test PDF is generated by `crates/core/examples/gen_fixtures.rs` into
  `crates/core/tests/fixtures/` (`cargo run -p nfsetable-core --example gen_fixtures`; it needs
  PDFium).
- The generator reproduces only the positions of real layouts (A4, points, top-left origin), with
  invented names, CNPJ numbers and amounts.
- To cover a new case, add it to the generator, regenerate, and commit the generated PDFs together
  with the code and the test.

## Updating the tax tables

Minimum wage, INSS ceiling, IRRF table, MEI values and Simples Nacional annexes change over time.
They live in `crates/core/tax/br.json`, in blocks with `valid_from`, `valid_to` and `source` (the
legal basis).

1. Add a block with the new validity without deleting the old one: the engine picks the block in
   force in the month being computed (the reference month), never by today's date. Blocks must be
   in chronological order without overlaps, so close the previous one with `valid_to`. If the file
   now covers more months, update `coverage` as well.
2. Cite the law or regulation in `source` and, if you could not confirm a number at the primary
   source, mark the block `"unverified": true`.
3. Add a case to `crates/core/tests/tax.rs` with every expectation computed by hand and the
   arithmetic written in the comments.
4. If the change affects what the UI shows, keep `app/src/lib/mock-tax.ts` (simplified figures for
   the browser) in step.

## Sending changes

1. Open an issue before large changes, so we can agree on the idea first.
2. Keep the pull request focused, with tests for what changed.
3. Go through the checklist of the PR template (formatting, clippy, tests and, if you touched the
   UI, `npm run check` and `npm run build`) and make sure no real invoice or personal data is in it.
4. When behavior changes, update README.md and README.pt-BR.md.
